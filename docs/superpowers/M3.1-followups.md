# M3.1 follow-ups — surfaced during Phase L (2026-05-11)

Phase L (E2E smoke) of M3 ran against `a5a79c6` (per-account bearer refactor)
and passed 6/6 tools, validated `workspace_id` filter, validated stale
endpoint detection. The following gaps surfaced during the recovery steps —
none block M3 from shipping, but they're worth attacking before exposing the
MCP surface to real external CLIs.

## 1. signOut + signIn (same runtime) leaves the MCP map in an inconsistent state — ✅ FIXED

**Status:** Resolved by splitting signOut from account-removal in the Rust
auth layer. signOut now uses a soft clear that drops the per-account access
token while keeping the bearer mapping intact, so the next sign-in (which
already re-pushes the access token via the `SIGNED_IN`/`TOKEN_REFRESHED`
listener) recovers without restart.

**Where the fix lives:**
- `src-tauri/src/mcp/auth.rs`: new `mcp_clear_account_access_token` Tauri
  command alongside the existing `mcp_remove_account_token`.
- `src/lib/mcp/index.ts`: new `notifyMcpAccountSignedOut`.
- `src/stores/auth-store.ts:348`: signOut now calls
  `notifyMcpAccountSignedOut` instead of `notifyMcpAccountRemoved`.
- Tests: Rust `soft_clear_drops_only_access_token`; vitest covers the
  signOut path in `mcp/__tests__/index.test.ts`.

**Why this is correct.** The bearer represents the *account identity*, not
the *session*. Removing the account from the app (AccountManager.remove)
still hard-revokes both via `mcp_remove_account_token`.

## 2. No proactive re-sync when Rust loses an account's access_token

**Severity:** STRONG.

**Reproduction.** Force-clear access_tokens in the Rust map (e.g. via
`mcp_remove_account_token`, or after a Rust-only restart while the front-end
keeps the session). The front-end has a valid Supabase session and won't
trigger `TOKEN_REFRESHED` until the natural expiry window (default ~60 s
before expires_at). Until then, every tool returns `auth_pending`.

**Suggested fixes (pick one):**
- (A) Add a `mcp_resync_account_token` Tauri command. Front-end calls it from
  `AccountManager.bootstrap()` and on app focus; Rust replies with the current
  expiry, front-end calls `supabase.auth.refreshSession()` if the gap is real.
- (B) On every `auth_pending` response, surface a UI hint with a "Force
  refresh" button that calls `supabase.auth.refreshSession()` then
  re-`notifyMcpAccountTokenChanged`. Simpler but reactive only.
- (C) Document the gap and rely on next natural refresh. Cheapest; punishes
  CLIs that hit the gap window with a confusing wait.

## 3. `mcp_remove_account_token` revokes both the bearer AND the access_token — ✅ RESOLVED

**Status:** Same fix as §1. The two commands now have clear, distinct
semantics:
- `mcp_remove_account_token` — hard revoke (account removed from app).
- `mcp_clear_account_access_token` — soft clear (session ended, account
  stays cadastrada).

To exercise the soft-expire path during a future Phase L re-run, call the
soft-clear command (via DevTools or a future programmatic hook). The next
tool call returns `auth_pending` as originally specified in the plan.

## 4. `workspace-manager bootstrap skipped — no active account/user` race

**Severity:** NIT (cosmetic).

The log message fires twice during normal sign-in — there's an effect that
calls `WorkspaceManager.bootstrap()` before `useAuthStore.user.id` is set. The
real bootstrap runs later via `syncOnLogin` and succeeds, so this is just
noise. Either gate the warn behind an actual error condition or remove the
log entirely.

## 5. `agents-store` fails to save to `AgentProfiles/profiles.json` after a cold-start

**Severity:** NIT (unrelated to M3; surfaced because Phase L started with a
cold-start).

```
Failed to save agent profiles: failed to open file at path: ...notter-ai/<acc>/AgentProfiles/profiles.json
with error: O sistema não pode encontrar o caminho especificado. (os error 3)
```

The `AgentProfiles/` subdirectory isn't created before the write. Add an
ensure-dir step in `agents-store.persist()`. Unrelated to M3 but worth a
one-line fix while we're here.
